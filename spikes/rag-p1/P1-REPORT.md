# P1-прогон суфлёра (offline, rag-core retrieval)

Дата: 2026-11-19. Раннер: `p1_run.cpp` (та же логика, что у live-worker: варианты
запроса + primary-entity буст + категория + FAQ fast-path + distance-гейт),
против копии индекса v2 (7789 чанков / 450 docs / 1174 FAQ / 109 паспортов).
Эмбеддинги: LiteRT embeddinggemma int8 (боевой рантайм приложения).
Сценарии: 19 из `dataset_p1_draft.jsonl` (16 signal + 3 no-data). Данные сценариев
и сырые результаты — локально (`~/rag-p1/`), в репозиторий не коммитятся (PII).

## Метрики

| Прогон | signal hit@6 | no-data silent |
|---|---|---|
| до фиксов | 11/16 (69%) | 0/3 |
| после фиксов | 13/16 (81%) | 0/3 |

Фиксы между прогонами:
- отраслевые вопросы («какие проекты/кейсы в …») → категория `cases`
  (`classifyCategory`: добавлены проект/делали/отрасл/сфер/направлен);
- `cases` бустит только `doc_type=case` (не prd) и сильнее (3×bonus) — иначе
  generic PRD/process страницы, лексически матчась на «проект», вытесняли кейсы;
- FAQ fast-path порог 0.35 → 0.20 (generic FAQ матчился на отраслевые и no-data
  вопросы на дистанции ~0.21–0.245 и вытеснял страницы проектов).

## Осталось (следующий шаг)

- **no-data не молчит (0/3).** Для отсутствующих отраслей (космос / шахты /
  авиакомпания) generic case-страницы и FTS всё равно дают карточки. Принципный
  фикс: для `cases`-вопросов резолвить отрасль через паспорта; если ни один
  паспорт не матчится (дистанция > порога) — возвращать пусто, а не generic
  case-поиск. Требует калибровки порога «вопрос → паспорт» на signal/no-data.
- **MISS 3/16** (мульти-ожидаемые сценарии): не все ожидаемые страницы в top-6;
  частично лечится тем же паспорт-резолвом отрасли + увеличением k для cases.

## Вердикт

Retrieval-ядро доведено до 81% hit@6 на P1; UX-вид (классический, доведённый)
согласован и внедрён отдельно. No-data гейт и мульти-ожидаемые MISS — следующая
итерация качества (не блокирует MR вида, но блокирует «качество суфлёра готово»).
