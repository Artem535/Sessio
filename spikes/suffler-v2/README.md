# Суфлёр v2 — две полосы (проект к обсуждению)

Схема: [`suffler-v2.html`](suffler-v2.html) (открыть в браузере; тёмная/светлая тема, экспорт PNG/SVG).
Исходник диаграммы: `suffler-v2.architecture.json`.

Предложение заменяет текущие 3–5 раздельных LLM-вызовов на батч одним multi-task
запросом и детерминированным retrieval-конвейером, работающим параллельно.
Ниже — пояснение каждой стадии и отличия от текущей схемы (`../rag-pipeline/`).

## Вход

- **ASR-транскрипт** — реплики звонка обеих ролей (как сейчас, `addPhrase` кормит все роли).
- **Батч-контроллер** — `CallPrompterController`: ≤6 фраз, debounce 1.5 с, бюджет окна
  ≤12000 символов. Не меняется.
- **Участники** — полоска сверху/сбоку вместо видео-плиток (пожелание клиента):
  основное окно отдаётся подсказкам и расшифровке. Чисто UI-задача, данных от модели не
  требует; на схеме — часть UI-региона.
- **Контекст запроса** — то, что модель получает помимо окна реплик: календарь +
  date_hints, records (записанные договорённости, для встроенного match), known_points
  (для дедупликации тезисов). Собирается контроллером из БД на GUI-потоке.

## Полоса A — один LLM-запрос на батч (PrompterWorker QThread)

**Один multi-task запрос.** Вместо `extract.txt` → `match.txt`×N → `deadline.txt` +
отдельный `live_points.txt` + per-phrase rewrite — один системный промпт и одна
объединённая JSON-схема:

```json
{
  "events": [{"kind": "accept", "participants": ["..."], "action": "...",
              "evidence_ids": ["..."], "meeting": true, "date": "YYYY-MM-DD",
              "time": "HH:MM", "target_id": "...", "unresolved": false}],
  "key_points": [{"text": "...", "evidence_ids": ["..."]}],
  "missing_deadline": {"missing": true, "evidence_ids": ["..."]},
  "context_requests": [{"kind": "project", "text": "производитель удобрений",
                        "evidence_ids": ["..."]},
                       {"kind": "question", "text": "он-прем и облако на проектах",
                        "category": "integration", "evidence_ids": ["..."]}]
}
```

Вход модели: окно реплик `[id] speaker: text`, календарь + date_hints (как сейчас),
**records** (уже записанные договорённости — чтобы модель сама делала match),
**known_points**. Движок: локальный LiteRT (LFM3/gemma int8, constrained decoding)
или облако с обезличиванием `Pseudonymizer` (имена клиентов/специалистов, телефоны, почты).

Отличия от текущей схемы:
- `match` встроен в запрос: точное текстовое совпадение остаётся fast-path в C++
  (`prompter_pipeline.cpp:594`), модели отдаётся только неоднозначное сопоставление.
- `context_requests` заменяет отдельный rewrite-вызов на каждую вопросительную реплику:
  модель выделяет из окна **типизированные** запросы контекста — `project` (описание или
  имя проекта, даже без имени: «производитель удобрений») и `question` (вопрос к wiki,
  чинит STT и разрешает анафору «а у них он-прем?»). Работает и на утверждениях без «?»
  («надо уточнять», «запрошу у коллег») — модель понимает intent вспомнить проекты.
- Роутер «вопрос/не вопрос» для полосы A не нужен — модель сама решает, что искать.

**Парсинг + валидация.** Как сейчас: проверка schema, evidence_ids против окна,
participants против спикеров, дат против календаря; невалидное событие отбрасывается,
невалидная дата теряется без потери договорённости. Результат распределяется:
events → карточки договорённостей, key_points → тезисы, missing_deadline → подсказка
«к какому сроку?», context_requests → в полосу B (пунктир на схеме).

## Полоса B — детерминированный retrieval без LLM (RagWorker QThread)

Стартует **сразу** на батче, не дожидаясь модели. Три источника входа в поиск:
имена проектов (NER, немедленно), описания проектов и вопросы (из полосы A,
`context_requests`, пунктир).

1. **NER-коррекция (`correctUtterance`, новая функция).** Каждый токен реплики
   сравнивается со словарём сущностей (кодпоинт-Левенштейн: cap 1 для ≥4 символов,
   cap 2 для ≥8, нормализация ё/регистра — механика уже есть в `entities.cpp`).
   Похожий токен заменяется каноническим именем → получается «предложение с правильным
   запросом» без обращения к LLM. Оригинал реплики остаётся вариантом поиска —
   страховка от ложных исправлений. Словарь — Entity-таблица индекса (1180 имён),
   на схеме — пунктир «словарь» index → NER-коррекция. Для упомянутой сущности
   сразу известны её primary-документы → страницы проектов попадают в панель
   без вопросительной формулировки.
2. **Embedder · batch.** Все варианты запроса (исправленный, оригинал, canonical-имена,
   описания и вопросы из полосы A) эмбеддятся одним вызовом `embed()`
   (gemma-2-270m int8, CPU, префиксы рецепта в rag-core).
3. **Резолвер + FAQ/RRF-поиск.** Три режима по kind запроса:
   - `project` с именем → primary-документы сущности (NER), без поиска;
   - `project` с описанием («производитель удобрений») → cosine эмбеддинга описания
     против **векторов ключей паспортов** (отрасль + тип клиента + что делали;
     длинное description размывает отраслевой сигнал — проверено гейтом) →
     страница проекта. Паспорта без отрасли — внутренние страницы, не проекты:
     в резолвер не попадают (109 из 186). Порог 0.25 калиброван гейтом:
     позитивы 0.11–0.22, отсутствующие отрасли 0.25+. При двух близких score
     (delta ≤0.05) возвращаем top-2 — клиент сам сказал «вернее даже два»;
   - `question` → FAQ fast-path (cosine-дистанция ≤0.35 → готовый ответ), иначе
     multi-variant RRF k=60: primary-буст (сущность главная в документе — кейс
     «Эвермаунт»), буст категории (cases/status/pricing/integration/navigation →
     doc_type), cutoff 0.02, doc-dedup по лучшему чанку.
4. Результат — **компактные ссылки** в панель контекста: заголовок проекта или
   FAQ-вопрос + URL. Snippet ≤600 знаков хранится для раскрытия.

Пунктир `context_requests` (полоса A → поиск): когда LLM-запрос вернулся, его
формулировки запускают уточнённый поиск; карточки обновляются, старые уезжают вниз.
Отмена устаревших результатов — по generation, как сейчас.

## Кейс клиента: проекты без имён

Реплика-эталон (ни одного имени, ни одного «?»):

> последние проекты где мы делали такую систему это был один сельскохозяйственный
> производитель, ну вернее производитель удобрений, один продавец строительных
> вернее отделочных материалов, вернее даже два, один производитель и второй именно
> строительный ретейл. Где там было онпрем развёртывание моделей а где обращение к
> облачным… И вот по использованным онперм моделям сейчас тоже не вспомню…

Что должна вернуть панель: **3 ссылки на страницы проектов + 2 ссылки-вопроса**
(«он-прем и облако на проектах», «он-прем модели на проектах»).

Почему текущая (v1) схема это не закрывает:
- NER ищет **имена**; «производитель удобрений» именем не является → матч пуст.
- Router v1 требует «?»/вопросительное слово; реплика — утверждение → поиск не стартует.
- RRF возвращает top-k **чанков** по одному запросу, а нужен **набор документов**
  (три разных проекта) + сквозной вопрос по ним.

Как закрывает v2:
1. Полоса A (LLM) читает окно и выдаёт `context_requests`:
   `project:"производитель удобрений"`, `project:"производитель отделочных материалов"`,
   `project:"строительный ретейл"`, `question:"он-прем и облако на проектах"`,
   `question:"он-прем модели на проектах"` — каждый с evidence_ids. Модель понимает
   intent «вспомнить проекты» даже без вопросительной формы.
2. Полоса B: три описания → резолвер по doc-векторам → три страницы проектов
   (какой именно проект, решает cosine, не хардкод).
   Два вопроса → FAQ fast-path: сквозные FAQ-пары, сгенерированные офлайн по **набору**
   статей (см. BACKGROUND), дают готовый ответ-сводку «где он-прем, где облако».
3. Панель показывает 5 компактных ссылок; клик по вопросу → вложенная панель со
   сводкой по трём проектам, клик по проекту → его страница.

Что должно существовать, чтобы кейс работал (и чего нет сегодня):
- **векторы ключей паспортов** в индексе — иначе описанию не с чем сравниваться;
- **сквозные FAQ** по наборам статей — иначе вопрос «где он-прем а где облако»
   вернёт чанк одного проекта вместо сводки;
- **context_requests в контракте** — иначе модель не отдаёт описания проектов.
Все три — части задач #8–#10, не отдельная магия.

### Результаты офлайн-гейта (19.11, VSellm-обогащение, GPU-эмбеддинги)

Описания → паспорта (ключ, фильтр отрасли, 109 паспортов):

| Описание | top-1 | top-2 | margin |
|---|---|---|---|
| производитель удобрений | проект A 0.115 | проект B 0.121 | 0.006 → top-2 |
| сельскохозяйственный производитель | проект C 0.185 | проект B 0.186 | 0.001 → top-2 |
| производитель отделочных материалов | проект D 0.187 | проект E 0.219 | 0.033 → top-2 |
| строительный ретейл | проект F 0.150 | проект D 0.206 | 0.056 → top-1 |

Вопросы → FAQ: «он-прем модели на проектах» → точный FAQ 0.039;
«он-прем и облако на проектах» → «На каких проектах было он-прем развёртывание?» 0.139
(порог fast-path 0.35). Ответ сквозного FAQ перечисляет проекты по развёртыванию
(один проект — он-прем, другой — облако и т.д.).

Негативы: «сеть кофеен» 0.311, «авиаперевозки» 0.251 (логистический оператор
семантически рядом); «металлургия» 0.215 — не негатив: металлургический клиент
реально есть в wiki. Отсюда порог 0.25. Остаточный шум: «сельскохозяйственный
производитель» top-1 проект C, но top-2 включает проект B — правило
неоднозначности страхует.

## UI — референс

- **Панель контекста** (правый сайдбар): набор компактных ссылок — страницы проектов
  (названия проектов) и FAQ-вопросы («он-прем и облако на проектах»).
  Не непрерывная лента: новые сверху, старый контекст уезжает вниз, но доступен.
- **Вложенная панель / модальное окно** по клику: ступенька влево от первого сайдбара,
  большое текстовое поле с полным ответом без пролистываний. Сразу видно все тейки
  модели — что она заметила и на что сформировала ответ.
- **Договорённости** — карточки как сейчас (принять/отклонить/сохранить заметку),
  плюс тезисы и подсказка про срок.

## BACKGROUND — индексация и обогащение

Две офлайн-стадии, на встрече не участвуют:

1. **Индексация.** Outline wiki → connector (ревизии, 429-retry, allowlist) →
   чанкер (1800 кодпоинтов, таблицы целы) → GPU-эмбеддинг на Buran → **LadybugDB v2**:
   Document (+doc_type, +primary_entity, **+doc-вектор** title+lead для резолвера
   описаний), Chunk, Entity (+primary_docs), **Faq** (вопрос/ответ/вектор).
2. **Генерация NER/FAQ.** Один GPU-проход lfm3 1.7B (vLLM :11438 на Buran) по статьям:
   роли сущностей (primary/mention), doc_type статьи, primary-документы, FAQ-пары
   вопрос/ответ — **включая сквозные вопросы по наборам статей** («он-прем и облако
   на проектах» → сводка по всем проектам с он-прем/облаком), не только per-doc.
   Результат (enriched.json) льётся в Entity/Faq/Document индекса — на схеме пунктир
   «Entity/Faq». Без этой стадии primary-буст, резолвер описаний и FAQ fast-path
   работать не могут: словарю нужны роли, Faq-таблице — пары, резолверу — doc-векторы.

Индекс v2 требует пересборки и замены при закрытом приложении (exclusive lock).
Словарь Entity читается полосой B при старте (`RAG: entities N`).

## Порядок внедрения и риски

1. **Cloud-first валидация контракта.** Объединённый промпт гоняем на облачной модели
   против текущих раздельных промптов на одних и тех же записях звонков; сравниваем
   events/points/queries по evidence и шуму.
2. **Retrain до мержа.** Локальная v11 обучена на per-task промптах; смена контракта =
   регенерация multi-task датасета + обучение (completion-only loss ON, урок v12).
   Пока модель не переобучена — объединённый режим только для облака, локальный
   работает на старом контракте.
3. **Риск схемы.** Вложенная multi-task схема на 1.7B с constrained decoding может
   просесть по качеству отдельных заданий — меряем на P1-прогоне, при просадке
   оставляем match отдельным refinement-вызовом.
4. **Не агентская система.** Фиксированный DAG: все шаги известны заранее, два QThread
   уже параллельны. Динамическое планирование не нужно — оно добавит латентность
   и непредсказуемость на встрече.
5. **Калибровка резолвера описаний.** Эталонную реплику клиента (и ещё 5–10 похожих)
   гоняем офлайн против реального индекса: подбираем порог doc-вектора и правило
   top-2. Риск: lead статьи не различает «производитель» и «ретейл» одной отрасли —
   тогда doc-вектор считаем по сгенерированному summary (lfm3), а не по сырому lead.
   Проверяем до GUI, как sanity-чек эмбеддингов на шаге 0.
