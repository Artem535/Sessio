= CPU spike: Gemma E2B — llama.cpp vs ONNX Runtime GenAI

Дата: 2026-10-09. Issue: https://github.com/Artem535/Sessio/issues/146.
Статус: пилот завершён; продуктовая интеграция и ASR/video-проверка не
выполнены.

== Решение

Для следующего локального CPU-пилота оставить *llama.cpp*. На данном
ноутбуке выбранный ONNX-пакет был примерно вдвое медленнее по медиане
полного ответа, потребовал значительно больше RAM и не улучшил
достоверность договорённостей. Это вывод о *конкретных поставках Gemma
E2B*, не обо всех ONNX-моделях. Ни один вариант пока не проходит
предложенную цель полного результата p95 ≤3 с.

== Метод и воспроизводимость

* Ryzen 7 7840HS, 27 GiB RAM, Fedora 44, governor `performance`; CPU
only. Radeon не инициализировалась. После прежнего GPU-сбоя была новая
загрузка ОС.
* llama.cpp `fc35562ba46fbbf8e30cac85edbb39642c37d248`, build 10635;
GGUF E2B Q4++_++0 из `ggml-org/gemma-4-E2B-it-GGUF`, revision `b4243c1`.
SHA256
`8e30dff3ac4c8434c49a7036fa15564bdbb6044e42bf04550bf1a096ad7e6a52`.
* ORT 1.31.0, ORT GenAI 0.17.1, Python 3.12.9;
https://huggingface.co/justinchuby/gemma-4-e2b-it-onnx[ONNX export]
`9bcf2cb1c2878b1c68a5f94db037272dfb278384`, `Q4++_++K++_++M/default`.
Все 14 файлов проверены по размеру; LFS-файлы также по SHA256. Embedding
SHA256
`7e2bc0ee31c7ccfca4184880af8487acdbf2670472683b9f946c65bc1e093e3f`.
* 4 intra-op/compute threads, 4K context, один запрос, до 160 выходных
токенов, greedy, thinking off, cache off, grammar off, одинаковый system
prompt.
* Шесть синтетических русских сценариев, 4 повтора каждого, один
исключённый warmup. Prompt 169–192 токена. Токенизация совпала по token
IDs при проверке tokenizer-файла ONNX и llama `/tokenize`; в измеренных
запросах совпали количества входных токенов. llama получал явный массив
token IDs.
* Runtime запускались последовательно; загрузка файлов/компиляция
завершилась до измерений. Обычные desktop-процессы оставались запущены.
* llama измерялся через `/completion` HTTP/SSE, ONNX через native GenAI
API. Таймер включает tokenization/generation; template rendering и model
loading вынесены отдельно. Локальный HTTP включён у llama.
* TTFT — первый непустой фрагмент текста. Он может быть началом
Markdown-блока, а не полезной подсказкой. Полная задержка — до конца
ответа, до удаления fence. Отрицания/дубли/evidence проверены вручную;
JSON validity не является quality score.
* p95 — интерполированный эмпирический percentile этих 24 запросов; это
не p95 реального звонка и не репрезентативная оценка разговорного
русского языка.

Квантизация различается: GGUF Q4++_++0 всего около 2.84 GB; ONNX
Q4++_++K++_++M квантует decoder (1.51 GB), но embedding data остаётся
5.53 GB, плюс audio/vision weights. ONNX использует весь мультимодальный
пакет для загрузки, но вход только текстовый. Разницу нельзя приписать
исключительно runtime или сравнивать как идентичные веса.

== Результаты

[cols=",>,>",options="header",]
|===
|Метрика |llama.cpp CPU |ONNX Runtime GenAI CPU
|Запросов после warmup |24 |24
|TTFT median, с |1.196 |1.980
|Полный ответ median, с |3.294 |6.579
|Полный ответ p95, с |5.158 |9.468
|Средняя занятость CPU, ядер |3.97 |4.75
|RSS в процессе генерации, приблизительно GiB |3.85 |13.44
|Строго валидный JSON без обработки |0/24 |0/24
|JSON после удаления Markdown fence |24/24 |24/24
|===

ORT user scope имел `MemoryMax=18G`, `MemorySwapMax=0`. Максимальный RSS
процесса по kernel high-water mark составил *15.50 GiB*, включая
загрузку. Пик памяти cgroup *17.59 GiB*, он включает cache и не равен
RSS. RSS sampling раз в 50 ms пропустил кратковременный максимум,
поэтому для ORT startup peak указан kernel HWM. У llama таблица отражает
наблюдённый RSS работающего сервера; startup peak отдельно не измерялся.
У ORT инициализация модели и tokenizer заняла около *10.70 с*. В конце
измерения системный swap был занят на 43 MiB; у самого ORT swap
запрещён.

Результат зависит также от длины ответа: ORT в некоторых сценариях выдал
больше токенов. Поэтому ниже приведены оба показателя. У llama
`tokens++_++predicted` включает терминальный шаг; ORT счётчик исключает
EOS. Разница в один шаг не объясняет существенные расхождения в длине.

[cols=",>,>,>",options="header",]
|===
|Сценарий |llama median, с |ORT median, с |llama / ORT выходных шагов
|Принятое время встречи |4.346 |7.507 |88 / 81
|Предложение встречи без согласия |2.231 |6.369 |32 / 66
|Исправленный срок |5.145 |9.464 |111 / 110

Даже при близкой длине ответа (исправленный срок) ONNX существенно
медленнее. В этом же сценарии синтетический decode-only rate не
измерялся отдельным тестом: полная задержка включает prefill и
завершение ответа.

== Содержание ответов

Оба варианта оборачивают JSON в `++```++json`: формат можно обработать
удалением fence, но это не исправляет фактические ошибки.

[cols=",,",options="header",]
|===
|Сценарий |llama.cpp |ONNX-поставка
|Время встречи |Время верное, evidence u1/u2 |Время верное, evidence u2

|Предложение без согласия |Встреча не зафиксирована |Записано «Проверить
расписание»; по строгой разметке этого теста ожидалось пусто

|Исправление срока |Понедельник верный, одна договорённость разбита на
две |Та же проблема с дублем

|Отрицание |Добавлено «Обсудим варианты», evidence пуст |Добавлено
«Обсудить варианты» по u2

|Принятое задание |Смысл правильный, evidence u2 |Смысл правильный,
evidence только u1 — предложение специалиста, без реплики согласия

|Погода |Пустой результат |«Сегодня пасмурно» ошибочно записано как
договорённость
|===

Различия в выводе при greedy могут быть связаны с экспортом,
квантизацией или реализацией вычислений. Эквивалентность logits/качества
исходным HF-весам не проверена. Нельзя утверждать, что ONNX как формат
«ухудшает модель». Шесть сценариев не дают статистически обоснованной
precision/recall. Определение самостоятельного обещания («проверю
расписание») требует отдельной продуктовой договорённости; ошибка с
погодой этой неоднозначности не имеет.

== Неуспешные и исключённые попытки

[arabic]
. Передача rendered prompt как строки в native llama API добавила второй
BOS. Прогон остановлен и исключён. Итоговый baseline использует явные
token IDs.
. Штатный ORT-пакет превысил cgroup limit 12 GiB при model load. Kernel
подтвердил `CONSTRAINT++_++MEMCG` / `oom-kill` для экспериментального
scope; host не падал.
. Отключение graph optimizations только у embedding также превысило 12
GiB. Эта попытка не дала throughput и не используется как результат
сравнения.
. Попытки отключить speech/vision через конфиг не загрузились: ошибки
отсутствующего `speech.filename` и попытка открыть directory вместо ONNX
model. Штатный мультимодальный экспорт нельзя превратить в text-only
одной этой правкой.
. Успешный ORT-прогон использовал штатные graphs/optimizations, лимит 18
GiB.

== Что делать дальше

Сначала сравнить E4B и Qwen 2B/4B через CPU llama.cpp и настроить
короткий вывод, строгую проверку evidence и дедупликацию. После выбора
модели повторить измерения с 2K/4K реального контекста, replay очереди и
одновременными ASR/audio/video.

Возвращаться к ORT для Gemma стоит с действительно компактным text-only
экспортом и квантизацией embeddings, с проверкой численной/семантической
эквивалентности. Это отдельная работа по экспорту модели; текущий
готовый пакет не даёт преимущества для суфлёра на этом ноутбуке.
GPU-прогоны остаются остановленными.

Код и команды: `spikes/live-llm-bench/README.md`. Сырые JSON, метаданные
и логи: локальный `spikes/live-llm-bench/results/` (gitignored). Не
содержит реальных клиентских данных.
