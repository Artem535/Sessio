= Rolling-window/state spike, 2026-10-09

== Probe

Same synthetic 2986-token conversation and pinned models as
xref:research/live-llm-long-results.adoc[the full-history experiment]. Split into
seven windows of whole utterances, up to 450 transcript tokens each, no
overlap or omitted lines. Replays start with empty state; every
subsequent state is generated by the model. No oracle/reference state is
injected. Two sequential replays per configuration. Fresh session per
update, four CPU threads, context 4096, greedy maximum 256 output
tokens. LiteRT uses MTP. No GPU execution selected.

First variant asks the model to return the complete current agreement
list, explicitly retaining previous agreements not mentioned by new
utterances. Second variant asks only for upsert/remove operations. Code
retains entries with no operations and applies updates by stable record
ID. Operations require nonempty evidence IDs known from previous/current
transcript, including at least one current ID. Rejected operations are
retained in the log, never silently applied. This checks provenance
syntax, not whether evidence semantically supports an operation. An
incorrect record ID can still duplicate an agreement.

An additional patch probe appends explicit rescheduling of the Friday
meeting from 18:00 to 20:00, cancellation of the Monday notes, and a
neutral weather turn. Expected end state: exactly one Friday 20:00
meeting. These extra turns are absent from the prior full-history
baseline and must be evaluated separately.

Different prompts, quantization, generated state sizes/output lengths,
and different workloads prohibit a controlled runtime-only comparison.
Per-update latency must not be confused with total replay time: many
short updates can require more total CPU than one full-history request.
Two replays and repeated synthetic filler do not establish
representative accuracy or production p95. The runner saves all
intermediate raw outputs, previous state, new window, decoded result,
rejection list, and resulting state under local results/.

Input including instructions/state: 574–791 tokens for LiteRT, 623–829
for llama; different generated states cause the counts to diverge. No
output hits the cap. Total replay time exceeds the one-shot full-history
request for both models, even though the per-update delay is shorter.
Short windows reduce perceived incremental delay while increasing total
repeated-prefill work.

LiteRT creates a Friday meeting (with empty evidence IDs), deletes it on
the next neutral window, creates Monday notes when those turns arrive,
and deletes them on the next neutral window. Its final state is empty in
both replays. Faster updates therefore do not make full-state
regeneration reliable.

llama also loses the Friday meeting at the first neutral window, then
promotes “новых задач или сроков не назначаем” to an agreement. It
creates Monday notes at their window, retains them once, and replaces
them with the neutral statement. Neither full-state variant meets the
agreement-preservation requirement.

== Operation/ledger results

Two replays of seven original windows plus three mutation windows: 20
updates per runtime. Latencies below include only the original
seven-window workload, so they are comparable in scope to the full-state
rows (14 observations each).

|===
|Export |First text median |Full update median |Mean sum per
seven-window replay
|LiteRT {plus} MTP, operations |1.448 s |1.616 s |11.475 s

|llama.cpp Q4++_++0, operations |5.019 s |5.350 s |36.583 s
|===

All ten steps' output text is identical across both replays of each
runtime. No output hits the token cap. All four configurations' outputs
parse after exact Markdown fence removal. Patch peak sampled RSS over
original{plus}mutation windows: LiteRT 1968 MiB (kernel high-water
2016656 KiB), llama server 4281 MiB.

LiteRT creates the Friday meeting with evidence a1/a2, preserves it
across neutral windows, but emits no operation for the accepted Monday
notes. After the original seven windows its state therefore has only one
of the two required agreements. It correctly upserts the meeting under
the same ID a1 with Friday 20:00 and evidence d1/d2. However, it then
emits `remove a1` with evidence e2, even though e2 cancels the notes,
not the meeting. The host provenance checks accept this wrong operation:
a1 exists and e2 is a real current utterance. Final state is empty.

llama emits empty operations throughout the original seven windows
(misses both facts), creates Friday 20:00 under d1 at the mutation
window, and deletes d1 on the unrelated cancellation of the notes. Final
state is also empty. Syntax constraints or stable IDs alone cannot make
these operations semantically safe.

== Verdict

Rolling windows materially reduce each update's delay; LiteRT with
operations is near the desired latency on this fixture. *Automatic
agreement state is not validated:* full-state regeneration loses
existing facts; operations miss new facts and can delete unrelated
records. The application-owned ledger helps with retention on empty
operations but does not solve semantic extraction or targeting.

For a product pilot, model changes should remain reviewable suggestions
until false creation, missed acceptance, incorrect correction, and
wrong-target removal pass a broader labeled evaluation. Potential
follow-up experiments: a stronger small model, simpler separate
extraction/correction tasks, explicit domain IDs with action-match
validation, and independent evidence verification. These are untested
hypotheses. KV reuse and simultaneous ASR/video remain untested too.

No Sessio product code, persistent storage, ASR/video, or real-time
scheduler was implemented. This code is an isolated throwaway experiment
under issue ++#++146.
