= Локальный суфлёр во время звонка: research и spike ++#++146

Дата: 2026-10-09. Статус: исследование; измерения ниже не означают
готовность продукта. Issue:
https://github.com/Artem535/Sessio/issues/146

== Рекомендация

Проверять *llama.cpp {plus} Gemma 4 E2B-it*, затем E4B-it и
Qwen3.5-2B/4B. Целевая машина: Ryzen 7 7840HS, Radeon 780M; сравнить CPU
(4/8 потоков) и Vulkan. Большая модель не должна быть первым выбором для
фонового суфлёра. Выбирать по задержке полезного полного результата и
качеству русского языка, а не только по tokens/s или общим академическим
benchmarks.

== Что подтверждено источниками

Gemma 4 существует; E2B/E4B имеют 2.3B/4.5B эффективных параметров, но
5.1B/8B с embeddings. Оба поддерживают 128K контекста и мультимодальный
ввод; лицензия Apache 2.0. Эти свойства не доказывают качество русского
суфлёра. https://ai.google.dev/gemma/docs/core/model_card_4[Google model
card].

llama.cpp поддерживает Gemma4: есть
https://github.com/ggml-org/llama.cpp/blob/master/conversion/gemma.py[конвертер]
и
https://github.com/ggml-org/llama.cpp/blob/master/common/parsers/gemma4.cpp[парсер].
Первый GGUF берём из репозитория самого runtime:
https://huggingface.co/ggml-org/gemma-4-E2B-it-GGUF/tree/main[Gemma E2B
GGUF], Q4++_++0 около 2.84 GB. Это размер файла, не итоговый расход RAM:
нужен ещё KV cache и рабочие буферы. Для текстового spike mmproj не
требуется.

Альтернативы — https://huggingface.co/Qwen/Qwen3.5-2B[Qwen3.5-2B] и
https://huggingface.co/Qwen/Qwen3.5-4B[Qwen3.5-4B]. Многоязычность
модели не заменяет проверку русских отрицаний, исправлений, дат и ролей
на наших сценариях. У Qwen3.5 thinking отключается параметром шаблона
`enable++_++thinking=false`; `/nothink` здесь не является
переключателем.

https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md[llama-server]
предоставляет SSE, структурированный JSON, переиспользование общего
префикса и настройки reasoning. JSON schema ограничивает форму, но не
истинность фактов.
https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md[llama-bench]
измеряет отдельно prompt processing и token generation;
https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md[Vulkan
build] позволяет проверить AMD GPU без предположения, что наличие Radeon
само даёт ускорение.

== Предлагаемый поток обработки

Аудиотреки → ASR → финализированные реплики с ID/ролью/временем →
планировщик → компактное окно последних реплик {plus} проверенное
состояние договорённостей → LLM → валидация evidence → карточки суфлёра.

Существующий ASR spike находится в другой ветке:
`docs/asciidoc/15-realtime-asr-spike.adoc` и `spikes/asr-model-bench/`.
Его GigaAM{plus}VAD результат можно использовать как входную гипотезу;
это не проверка совместной нагрузки с LLM. Нативное аудио Gemma стоит
вынести в отдельный эксперимент: аудиовход модели не доказывает
streaming ASR.

Предлагаемый режим: один запрос в работе, изменения реплик объединяются;
для подсказок устаревшие запросы заменяются свежими. Договорённости
обрабатываются по непрерывному watermark реплик, чтобы объединение
очереди не теряло события. Каждый результат несёт transcript revision и
evidence IDs. Старые результаты не публикуются поверх новых.
Предложения, отрицания и исправления проверяются раздельно; исправления
заменяют предыдущую запись с сохранением evidence.

Суфлёр выдаёт максимум 1–2 короткие карточки: вопрос для уточнения,
напоминание о незавершённой теме или явно принятую договорённость. Для
обычной реплики разрешён пустой результат. Договорённости —
редактируемые черновики; модель не должна автоматически записывать их
как подтверждённые факты в карточку клиента. Это проектная рекомендация,
не реализованное поведение Sessio.

Начать с 4K контекста, затем 8K; не переписывать весь час разговора на
каждом запросе. Стабильный system prefix {plus} компактное состояние
{plus} последние реплики. Thinking отключить. Ответ ограничить 80/160
токенами. Сжатие истории измерять отдельно: оно само стоит времени и
может потерять важное отрицание.

[arabic]
. Gemma E2B Q4++_++0: CPU 4/8 потоков и Vulkan Radeon; затем тот же E4B.
. Qwen3.5-2B/4B: сопоставимые четырёхбитные GGUF, точно зафиксированные
источники/ревизии/квантизация; сравнение разных квантов явно
подписывать.
. Prefill 512/2048/4096 и decode 80/160 токенов; 5 повторов после
warmup.
. API: cold prefix и cached prefix раздельно; короткий и 2K/4K prompt,
TTFT до первого content token и время до полного валидного JSON.
. Replay 30–60 минут, реплики каждые 2/5/10 секунд, burst и перебивания;
очередь, watermark, отмены, дубли и устаревшие результаты.
. Повторить рядом с 2 ASR-треками и настоящим двухсторонним
видеозвонком: ASR phrase lag, потери аудио, video frame drops, CPU/RSS,
GPU/shared RAM, температура/троттлинг. Vulkan конкурирует с видео за
ресурсы общей памяти.

Скорость должна включать prefill и полный вывод. Грубая модель задержки:
`ASR lag {plus} debounce {plus} queue wait {plus} prefill {plus} output++_++tokens / decode++_++rate {plus} validation`.
Например, 80 токенов при 20 tokens/s требуют 4 секунды только на вывод;
это арифметический пример, а не замер этого ноутбука.

== Качество и предлагаемые критерии выбора

Собрать 100 обезличенных/синтетических русских сценариев с независимой
ручной разметкой: согласие, отказ, предложение, исправление срока,
неизвестный владелец, отмена обязательства, несколько участников,
ASR-ошибки, обычная беседа, инструкции внутри цитируемой реплики.
Считать agreement precision/recall и правильность
владельца/срока/evidence. Подсказки оценивать человеком по уместности и
полезности; пустой ответ может быть правильным.

Предлагаемые, пока не утверждённые gates: полный результат p95 ≤3 с от
финальной реплики; agreement precision ≥95%, recall ≥85%; нет выдуманных
владельцев/сроков в контрольных случаях; очередь не растёт; ASR p95
ухудшается ≤20% относительно того же теста без LLM. Порог 3 секунды не
означает пословную реакцию на речь. Нужен отчёт о цене пропусков при
принятой политике планировщика.

== Воспроизводимость и границы

Код в `spikes/live-llm-bench/`, отдельно от CMake приложения. Модели и
сырые результаты вне коммита. Фиксировать llama.cpp SHA, model SHA/hash,
CPU/GPU/driver, контекст, потоки, offload, batch, quant, sampler, cache
policy и фоновые процессы. Первые шесть синтетических API-сценариев
являются smoke, не статистической оценкой качества. Реальные клиентские
реплики не использовать в репозитории.

== Измерения этого запуска

Первый пилот: Gemma E2B Q4++_++0, llama.cpp SHA
`fc35562ba46fbbf8e30cac85edbb39642c37d248`, build 10635, CPU 4 потока,
без GPU offload. Модель из `ggml-org/gemma-4-E2B-it-GGUF`, revision
`b4243c1`, SHA256
`8e30dff3ac4c8434c49a7036fa15564bdbb6044e42bf04550bf1a096ad7e6a52`.
Рабочая Fedora 44, RAM 27 GiB. На машине работали обычные приложения,
включая VM; это не чистый лабораторный стенд. Логи и JSON находятся в
локальном `spikes/live-llm-bench/results/` (gitignored).

`llama-bench`, pp512 / tg80, 3 повтора: *152.82 input tokens/s, 28.08
output tokens/s*. Это синтетическая скорость, не full-call latency.

API: 4096 context, max++_++tokens=160, temperature=0, seed=146,
reasoning off, cache++_++prompt=false, warmup и по одному запуску шести
коротких сценариев.

[cols=",>,>,",options="header",]
|===
|Сценарий |Первый content token, с |Полный JSON, с |Ручная проверка
|Принятое время встречи |1.40 |4.51 |Срок и обе реплики сохранены

|Предложение без согласия |1.32 |2.38 |Договорённостей нет; подсказка

Все шесть ответов синтаксически валидны, но семантический контроль не
пройден. Полный результат 1.93–5.34 с, это *диапазон шести
smoke-запросов, не p95*. Время отсчитано от HTTP-запроса:
ASR/debounce/очередь/UI не включены. Первый пилот выполнен до запуска
Vulkan-компиляции. Cached exploratory run во время компиляции
исключается из сравнения скорости как загрязнённый нагрузкой.

Вывод пилота: локальный E2B физически запускается; готовность суфлёра и
качество фиксации договорённостей не подтверждены. Нужны настройка
prompt, дедупликация, проверка непустых evidence и сравнение с E4B/Qwen.
Vulkan и совместная ASR/video-нагрузка оцениваются отдельно.

=== Сбой при попытке Vulkan: дальнейшие GPU-прогоны остановлены

Vulkan-сборка успешно завершилась, но сразу после попытки GPU benchmark
пользователь сообщил о краше компьютера и появилась новая загрузка ОС. В
`e2b-vulkan-bench.log` сохранилась только инициализация Radeon 780M RADV
PHOENIX; `e2b-vulkan-bench.json` пуст. GPU throughput не измерен.
Попытка использовала `-ngl 99 -dev Vulkan0`, тот же E2B Q4++_++0.

Доступный журнал ядра предыдущей загрузки не содержит подтверждения OOM
или GPU reset в момент сбоя. Поэтому связь по времени есть, но причина
(драйвер/runtime/давление памяти/иной сбой) *не установлена*. Перед
экспериментом RAM была занята примерно на 20/27 GiB, swap 8 GiB
полностью занят; это отдельный фактор, не доказательство OOM. После
перезапуска активных llama-bench/llama-server не найдено. Vulkan
автоматически не повторять. Первые CPU-результаты остаются пригодны как
ограниченный smoke; ускорение на Radeon и стабильность всего контура
открыты.

[[продолжение-cpu-llamacpp-против-onnx-runtime-genai]]
== Продолжение: CPU llama.cpp против ONNX Runtime GenAI

После сбоя GPU пользователь согласовал CPU-сравнение. GPU-процессы не
запускаются. ORT окружение изолировано в cache; версии: onnxruntime
1.31.0, onnxruntime-genai 0.17.1, Python 3.12.9. Модель:
https://huggingface.co/justinchuby/gemma-4-e2b-it-onnx[`justinchuby/gemma-4-e2b-it-onnx`],
revision `9bcf2cb1c2878b1c68a5f94db037272dfb278384`, вариант
`Q4++_++K++_++M/default`. Это сторонний экспорт той же исходной Gemma
E2B, опубликованный автором экспорта
https://github.com/onnxruntime/mobius/issues/346[Mobius], а не
официальный benchmark Google на нашем ноутбуке.

В ORT-пакете INT4 относится к decoder; файл embeddings 5.53 GB, decoder
data 1.51 GB, audio encoder 0.61 GB, vision encoder 0.36 GB. Для GGUF
E2B Q4++_++0 весь файл 2.84 GB. Квантизация двух поставок отличается;
пакет ONNX не следует описывать как целиком четырёхбитную модель. Нельзя
приписать разницу скорости исключительно runtime.

Метод: 4 потока, 4096 context, один запрос, 160 выходных токенов,
greedy, без thinking/cache/JSON grammar, одинаковый rendered prompt из
ONNX `chat++_++template.jinja`. 6 сценариев × 4 повтора после одного
warmup. Прежний schema-constrained API smoke не является парным baseline
для этого теста. llama.cpp используется через `/completion` HTTP/SSE;
ORT — через Python GenAI API. Одинаковость количества входных токенов
проверяется отдельно. HTTP накладные расходы включены у llama,
Python/tokenizer — у ORT. Память: RSS процесса llama-server и RSS Python
ORT каждые 50 ms, включая warmup. Запуск моделей раздельный, без
компиляций/загрузок весов во время измерений. Первый ORT запуск имел
`MemoryMax=12G`, `MemorySwapMax=0` и превысил лимит при загрузке.
Успешный прогон имел лимит 18 GiB при примерно 22 GiB доступной RAM;
лимит относится к эксперименту, не меняет глобальные настройки ОС.

CPU-сравнение завершено: полный ответ median/p95 *3.294/5.158 с* у
llama.cpp и *6.579/9.468 с* у выбранного ONNX-пакета. Последний превысил
лимит 12 GiB при загрузке; успешный запуск потребовал scope с лимитом 18
GiB и дал kernel peak RSS 15.50 GiB. Для следующего CPU-пилота
рекомендуем llama.cpp. Полный метод, содержание ответов, память и
ограничения: xref:research/live-llm-cpu-results.adoc[CPU spike results]. Совместная
ASR/video-нагрузка в этот CPU-пилот не входит.
