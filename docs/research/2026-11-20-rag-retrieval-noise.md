# RAG: природа «мусора» в выдаче и почему паспортный no-data гейт не сработает

Дата: 2026-11-20. Ветка: `feat/185-rag-core` (HEAD `f4d62c23`).
Индекс: копия v2 `~/.cache/sessio-rag/index-v2-copy.lbug` — 450 docs / 7789
чанков / 1174 FAQ / 109 паспортов. Эмбеддинги: LiteRT embeddinggemma-2 (270m).
Метод: офлайн-прогон той же логики, что у живого worker (`variants + primary
entity boost + category + FAQ fast-path + distance gate`), с разбором
промежуточных величин (base RRF, dense distance, fts-флаг, бусты).

## TL;DR

«Мусор» — это не отсутствие релевантных страниц, а несколько классов
не-ответных документов, которые вытесняют ответ. Главная причина — **буст
категории `cases` (+0.0492) доминирует над базовым RRF (0.02–0.05)**: он
поднимает generic-деки и low-relevance `case`-страницы выше реально
релевантных `prd`/`process`/`kp`. Вторая причина — **FTS-only совпадения
обходят dense-гейт**, из-за чего в карточки попадают опросники, чеклисты,
summary и бэклоги.

План из `spikes/rag-p1/P1-REPORT.md` — no-data гейт по cosine-дистанции
«вопрос → паспорт» — **эмпирически не разделяет** signal и no-data (см. §6).
Его нельзя реализовывать в текущем виде.

## 1. Как устроена выдача

`src/rag/search.cpp: searchWikiBoosted`:

1. Для каждого варианта запроса — embed (`task: search result | query: …`),
   затем dense top-50 и FTS top-50.
2. RRF-фьюжн (`kRrfK = 60`), ранг каждого попадания складывается в score чанка.
3. Dedup по документу: остаётся лучший чанк документа.
4. Буст `+1/61` за primary-сущность (`boostDocIds`).
5. Буст категории: `cases` → `+3/61 ≈ +0.0492`, прочие → `+1/61 ≈ +0.0164`.
6. Сортировка, отсечение `k`, distance-гейт: `!fts && dense > 0.5` отбрасывается.

Живой `rag_worker.cpp` до этого добавляет LLM-rewrite (query/category/projects),
FAQ fast-path (`≤ 0.20`) и `resolvePassports` по описаниям проектов из rewrite.

`classifyCategory` (`rewrite.cpp`) проверяет `cases` **первым**: «кейс|пример|
клиент|внедрен|проект|делали|отрасл|сфер|направлен».

## 2. Что именно «мусор» (конкретные карточки)

### S6 — вопросы про отсутствующие отрасли (ожидается пусто)

| Вопрос | Топ выдачи | base RRF | dense | fts | cat-буст | final |
|---|---|---|---|---|---|---|
| космос | Клиент A — «Общая презентация кейсов» | 0.0147 | 0.242 | 0 | +0.0492 | 0.0639 |
| космос | Кейс HR-автоматизации | 0.0094 | 2.000 | 1 | +0.0492 | 0.0586 |
| космос | Вопросы к заказчику | 0.0400 | 2.000 | 1 | 0 | 0.0400 |
| шахты | Оценка эконом. эффекта… (БТ) | 0.0260 | 0.247 | 0 | +0.0492 | 0.0752 |
| шахты | Кейс стади для производства | 0.0241 | 0.250 | 0 | +0.0492 | 0.0733 |
| шахты | Кейсы по кастдеву | 0.0238 | 0.251 | 0 | +0.0492 | 0.0730 |
| авиакомпания | Кейсы по кастдеву | 0.0312 | 0.262 | 0 | +0.0492 | 0.0804 |
| авиакомпания | Кейс стади для производства | 0.0308 | 0.265 | 0 | +0.0492 | 0.0799 |

Во всех случаях буст категории — это 2/3–4/5 итогового score.

### S1 — «какие кейсы в отелях» (ожидается 2 релевантные страницы)

- #1 `Кейсы по кастдеву` — generic-дек, base **0.0230** + 0.0492 = **0.0722**.
- #2 `ULTRA Lean PRD: … гостиничных объектов` — релевантный отельный PRD,
  base **0.0494**, без буста = 0.0494.

То есть generic-дек с базой в 2 раза ниже обгоняет релевантный документ только
за счёт `doc_type=case`.

## 3. Корневые причины (ранжированно)

1. **Буст категории применён безусловно.** Любой документ с
   `doc_type == case` получает +0.0492, независимо от того, насколько он
   релевантен запросу. Базовые RRF для кейсов систематически ниже (0.02–0.03),
   чем у generic-PM-страниц (0.04–0.05), поэтому плоский буст и нужен, но он же
   поднимает generic-деки.
2. **FTS-only попадания обходят distance-гейт.** У `Вопросы к заказчику`,
   `Кейс HR-автоматизации`, `Summary`, `бэклог` dense = 2.0 (только лексика), но
   они попадают в карточки. Опросники/чеклисты/саммари — это не ответ.
3. **`classifyCategory` слишком жадный.** Навигационные вопросы с «проект»/
   «направлен» становятся `cases`:
   - «Где у нас лежат КП и оценки по проектам?» → `cases` (должно `navigation`);
   - «Где найти договоры по AI-направлению?» → `cases`.
   Из-за этого буст засоряет навигационные ответы (S5: в топе обзор ML-кейсов
   и презентация клиента A).
4. **Generic-деки размечены как `case`.** «Кейсы по кастдеву», «Кейс стади для
   производства», «Общая презентация кейсов», «Агрегатор 3 кейсов» — это
   агрегаторы, а не конкретные клиентские кейсы. Проблема уровня enrichment,
   не retrieval.

## 4. Что НЕ является причиной

- **Dense distance сам по себе не отделяет мусор.** У generic-дека «Кейсы по
  кастдеву» dense = 0.26 — он семантически близок к «какие кейсы», поэтому
  порог по расстоянию его не отсечёт.
- **Score-порог тоже не работает.** No-data мусор (0.04–0.08) перекрывается с
  валидными сигналами (0.07–0.11).

## 5. Почему это важно сейчас

По `spikes/rag-p1/P1-REPORT.md`: hit@6 = 81%, no-data silent 0/3, MISS 3/16.
No-data 0/3 — это ровно те S6-карточки выше. В отчёте прямо сказано, что это
блокирует «качество суфлёра готово».

## 6. Отрицательный результат: паспортный no-data гейт не разделяет

P1-отчёт предлагал: для `cases`-вопроса резолвить отрасль через паспорта; если
дистанция > порога — молчать. Проверено на 109 паспортах (эмбеддинг паспорта —
`industry. client_type. what_built`, как в `indexer_v2.py`).

Минимальная cosine-дистанция «вопрос → ближайший паспорт»:

| Форма запроса | signal (диапазон) | no-data: шахты / космос / авиакомпания |
|---|---|---|
| raw question | 0.212–0.333 | 0.226 / 0.287 / 0.308 |
| rewriteQuery | 0.212–0.333 | 0.226 / 0.287 / 0.308 |
| фраза после предлога | 0.206–0.348 | 0.238 / 0.278 / 0.281 |

Ни один порог не разделяет: no-data «шахты» (0.226) **ближе к паспорту**, чем
валидные «гостиницы» (0.245), «ритейл» (0.271), «HR» (0.284), «медицина»
(0.305); а «космос» (0.287) и «авиакомпания» (0.308) перекрываются с валидными
«HR» (0.284) и «медицина» (0.305).

Причина: паспортный эмбеддинг описывает компактную отрасль, а вопрос содержит
вопросную оболочку; абсолютная близость не кодирует «такая отрасль у нас есть».
Плюс в паспортах есть `горнодобывающая компания`, поэтому лексический вариант
тоже пометил бы «шахты» как «есть» (хотя P1 считает это no-data — разметка
спорная: подбор кандидатов для горнодобывающей — валидный кейс).

Важно не путать: `resolvePassports` для **описаний проектов из LLM-rewrite**
(«производитель удобрений») — это отдельный рабочий путь, он не про no-data.

## 7. Рекомендации (по убыванию эффекта/чистоты)

Пометка: **[код]** — `src/rag/search.cpp` / `rewrite.cpp`; **[данные]** —
`spikes/rag-indexer` + `enrichment` + переиндексация.

1. **[данные] Переклассифицировать generic-деки и boilerplate.** Ввести в
   enrichment `doc_type` (или флаг `answerable`) для «кейсы по кастдеву / кейс
   стади / общая презентация кейсов / агрегатор 3 кейсов» → не `case`, и для
   опросников/чеклистов/summary/бэклогов → `working`, не `case`. Тогда буст
   перестанет их поднимать. Самый чистый путь, но нужна переиндексация.
2. **[код] Сделать буст условным, а не плоским.** Например, применять
   `3×bonus` только к кейсам из top-N по base, либо ограничить
   `score = base + min(boost, α·base)`. Требует калибровки на P1 **с expected
   URL** (в репозитории их нет, лежат локально).
3. **[код] Отсекать boilerplate и слабые FTS-only.** Либо требовать dense-
   поддержку (кроме очень сильного base), либо штрафовать/фильтровать по
   title-паттернам: `вопросы`, `опросник`, `чеклист`, `summary`, `бэклог`,
   `задачи`. Это убирает S6-«Вопросы к заказчику», «Summary», «бэклог проекта».
4. **[код] Приоритет навигации в `classifyCategory`.** Проверять
   `где|найти|папка|лежит|документ` раньше `проект|направлен`. Чинит засорение
   S5, риск регрессии низкий (отраслевые вопросы без навигационных слов
   остаются `cases`).
5. **[код+данные] No-data guard только через отраслевой словарь, не
   эмбеддинги.** Собрать из паспортов множество отраслей/алиасов, извлекать
   отраслевую фразу из вопроса и проверять лексически (со стеммингом). Даёт
   2/3 на S6; ограничение — синонимы и спорная разметка «шахт».

## 8. Как воспроизвести

- Индекс: `~/.cache/sessio-rag/index-v2-copy.lbug`
- Extensions: `~/.cache/sessio-rag/ladybug/extension/{fts,vector}`
- Модель: `~/.cache/sessio-rag/models/embeddinggemma-2-text-270m.litertlm`
- Сценарии: `~/rag-p1/results2.jsonl` (19 шт.; expected URL — локально).
- Прогон: воспроизвести `searchWikiBoosted` на этих входах и печатать
  `base / dense / fts / ent / cat / final` по каждому документу. Офлайн-пробы
  использовали `IndexStore::{searchVector,searchFts,documentInfo,allPassports}`
  и `sessio_litert::loadEmbedder`; линковка — `libSessio_rag_index.a`,
  `libSessio_rag.a`, `libsessio_litert.so`, `liblbug.so`.

## 9. Ограничения

- P1 `expected_docs` в репозитории отсутствуют (PII), поэтому hit@k здесь не
  пересчитывался; оценивались конкретные карточки и их вклад base/буст.
- Разметка «шахты = no-data» сомнительна при наличии паспорта горнодобывающей;
  перед внедрением no-data guard её нужно перепроверить.
- Любая правка retrieval должна прогоняться на P1-раннере с expected URL,
  иначе нельзя гарантировать сохранение 81% hit@6.
