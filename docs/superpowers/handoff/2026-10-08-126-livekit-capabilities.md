# Screen sharing #126: LiveKit capability gate

**Decision 2026-10-08: superseded.** The one-owner lease is dropped. Any
participant may share a screen at the same time, so no permission is revoked
mid-call and the cached-grant counterexample below no longer matters: tokens
are issued once with the default grants (camera, microphone, screen). Nothing
in this document needs to be enforced by the server. Limiting simultaneous
screens, if ever needed, is a UI-level soft limit. The analysis below is kept
as the record of why the lease was abandoned.

**Result: BLOCKED.** Selective source permission updates work in the current
connection, but a cached server-issued grant JWT restores screen permission on
a new connection after revocation. The approved self-hosted lease design cannot
provide its server-authoritative one-owner/expiry guarantee with this mechanism.
Publishing implementation stops at this gate; no production services contacted.

## Assertions and counterexample

1. Original join JWT allows only `camera` and `microphone`. Both are published;
   baseline screen publication is rejected by the client SDK.
2. RoomService grants `CAMERA`, `MICROPHONE`, `SCREEN_SHARE`. The server observes
   three track publications. The SDK receives an automatically refreshed JWT,
   now containing `screen_share`; the test saves that JWT in memory.
3. RoomService returns permissions to `CAMERA`, `MICROPHONE`. The actual screen
   publication disappears. Both original camera/microphone track SIDs remain.
   A screen republish in this current connection is rejected by the SDK.
4. Disconnect the owner and join the same room/identity with the JWT saved in
   step 2, without asking the application backend for a new token. The server
   accepts this new connection and reports screen publishing allowed again.
5. Publish a new screen track. `GetParticipant` confirms **one SCREEN_SHARE
   publication**. The saved JWT still has approximately **596 seconds** until
   expiry. The test fails its security assertion and exits **1**.

Output from the final HTTPS/WSS run, excluding stack trace:

```text
Browser 156.0.8078.4; SDK 2.22.3
PASS baseline camera/mic published; screen denied
PASS selective screen grant publishes third track
OBSERVED selective revoke: camera/mic SIDs preserved; 0 screen track(s) remain; allowed sources ["CAMERA","MICROPHONE"]
PASS selective revoke removed screen while preserving camera/mic
PASS connected owner screen republish denied after revoke
OBSERVED server-refreshed JWT screen grant true; TTL approximately 596 seconds
OBSERVED old grant-token new connection allowed sources ["CAMERA","MICROPHONE","SCREEN_SHARE"]
OBSERVED old grant-token screen publication count 1
Error: CAPABILITY BLOCK: old server-refreshed grant JWT permits screen publication after revoke on a new connection
```

This is a new join using a cached JWT, not a claim about automatic SDK resume.
The track SID assertions establish publication preservation, not uninterrupted
real-device playback or ASR quality. No actual lease HTTP routes were involved;
the gate directly exercises the server primitive on which those routes depend.
The original baseline token is safe; the **server-refreshed token generated by
the temporary grant** is the demonstrated bypass. Restricting all original
application-issued JWTs to camera/microphone does not remove this counterexample.

## Why session/SID checks and reconciliation do not close the gap

Inference from the observed primitive: call-session SID binding can reject an
application acquire/renew request from a replacement connection, but the cached
JWT holder does not call those endpoints. LiveKit accepts and authorizes the
media connection itself. Polling/webhooks can discover and revoke it later;
they cannot guarantee that the unauthorized track is never published between
admission and reconciliation. If the room has already handed its lease to another
owner, this creates a window for two presentations. That two-owner race was not
run here; the underlying unauthorized publication was observed directly.

Retaining `Revoking` until the first screen disappears does not solve a later
rejoin after the room returns to `Free`. Refusing all handovers for the refreshed
token lifetime changes the 20-second expiry/UX contract and is not an approved
solution. `canPublish=false` would also remove camera/microphone and violates the
explicit independent-media requirement.

## Design alternatives requiring a decision and a new gate

- Add server-side revocation/admission enforcement to the self-hosted LiveKit
  deployment. Cached grant JWTs must fail before publication on every full join
  and resume path, including after server/backend restart. Cost: server changes
  or a strictly enforced signaling admission layer, upgrade maintenance and
  fail-closed availability. A proxy alone is insufficient if direct server
  admission remains reachable; all paths and refreshed tokens need enforcement.
- Evaluate a service with actual token revocation support, such as LiveKit Cloud.
  Cost: infrastructure/privacy/cost decision and fresh selective revoke/reconnect
  evidence. Current documentation describes a default revocation time buffer;
  migration by itself is not proof of strict immediate lease enforcement.
- Separate a screen-only publishing participant from the camera/microphone
  participant, combined with authoritative admission/revocation. Cost: changed
  identity/ownership model and extra connections. A separate identity **alone**
  still leaves self-hosted cached screen JWTs valid and does not fix this gate.

No alternative is selected or implemented. Cooperative UI stop, disabled controls,
short application session TTL and later cleanup are not substitutes for the
approved server-authoritative guarantee.

## Primary documentation

The observed refresh and self-hosted limitation agree with
[LiveKit token lifecycle](https://docs.livekit.io/frontends/reference/tokens-grants/#token-lifecycle):
permission updates trigger refreshed tokens, refreshed lifetime is at least ten
minutes, and self-hosted permission updates do not invalidate existing JWTs.
That documentation also identifies token revocation as Cloud-specific and
describes its cutoff/buffer behavior. Checked 2026-10-08; live runtime above is
the evidence for the pinned self-hosted version.
