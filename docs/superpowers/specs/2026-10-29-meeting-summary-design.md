# Live key points during the call, full meeting summary after it

Continues #151 (call prompter) and `2026-10-19-call-notes-key-points-design.md`.

## Intent

A real 30-minute test call showed the live notes pipeline doing too much at
once. After every batch of phrases it reran `processNotes` over the whole call
so far, rebuilding a 160-character note and up to 4 key points. The model was
busy with a summary nobody reads while the call is running. The summary that
appears after the call is then the same short note, because the final run uses
the same pipeline and the same output shape.

The specialist's words: a short summary during the call is not needed, but a
big, full summary after the call is. During the call, the useful things are the
ones the specialist can still act on while the client is on the line: key
points as they come up, and agreements, including the next meeting. The next
meeting should become a calendar event in one step.

## Goals

1. **During the call** the notes pipeline produces only **key points**,
   incrementally. Each run reads only the phrases that arrived since the last
   run, so earlier points never change or disappear. No running summary.
2. **Agreements** keep working live as they do today: extraction, matching
   against earlier agreements, and review cards. An accepted agreement that is a
   **meeting** gets an **«Add to calendar»** button. It opens the normal
   new-event dialog with the date, time, client and title filled in. The
   specialist checks the values and saves. Nothing is created without that save.
3. **After the call** the notes page offers **«Summarize meeting»**. One click
   runs a full summary over the whole transcript. It does not start on its own.
4. The full summary has four sections:
   - **Overview.** 1–2 coherent paragraphs, about 600–1000 characters: what the
     client came with, what was discussed, where it ended up.
   - **Key points.** Up to 10 facts across the whole call.
   - **Agreements and tasks.** First the agreements the specialist accepted
     during the call (the reviewed ledger), then the extra tasks the model
     found in the transcript, without repeats of accepted ones. Only accepted
     agreements have «Add to calendar». A summary task has «Accept», which
     moves it into the agreements ledger, where it gets «Add to calendar».
   - **Open questions.** What stayed unclear or is worth returning to next
     time.
   Every item links to its source phrases, as today.
5. Both sets of key points are shown after the call: the live ones collected
   during the call, and the summary's own.
6. The summary can be re-run. The existing "transcript changed → Update" (stale)
   logic keeps working.
7. Every model reply is schema-constrained: a LiteRT-LM llguidance JSON schema
   via `DecodeConfig::SetConstraint`, with schemas generated by reflect-cpp, as
   `call_notes_pipeline.cpp` already does. This covers the new live-points and
   summary calls, and also the agreement calls (extract, match, deadline), which
   are unconstrained today.
8. EN/RU translations for all new strings (`translation/app_en.ts`,
   `translation/app_ru.ts`).

## Non-goals

- Live hints backed by a search of the specialist's data ("has this client had
  such projects before?"). That is parts 2–3 of
  `2026-10-27-web-calls-kb-hints-cloud-design.md` and is brainstormed
  separately.
- Creating calendar events automatically, without the specialist's save.
- Migrating saved summaries. Old meetings keep their short summary and show it
  as before. «Create again» rebuilds it in the new format.
- Cloud models or a larger model.

## Anti-goals (a failure even if it technically works)

- Something lands in the calendar that the specialist did not confirm.
- The summary starts on its own after the call and holds the model or CPU
  without being asked.
- Live key points reshuffle, rewrite or vanish during the call.
- The summary contains advice, diagnoses, judgements of mental state, inferred
  intentions or invented commitments. The current prompts' rules stay.
- An existing saved summary disappears or breaks after the update.

## Constraints

- On-device Gemma 4 E4B through `libsessio_litert`, 4096-token context
  (`sessio_litert.h` `contextTokens`), greedy decoding. One `PrompterWorker`
  serves the agreement prompter, live notes and the finalizer.
- Every request keeps the current safeguards: request identity
  (token/request_id/generation/ledger_revision), source-ID validation against
  the input, rejection of unusable replies, the consent/revoke and
  transcript-deleted paths, and the stale check against the current phrases.
- Long calls still need chunking. The summary must cover the whole call,
  including late facts. A chunk the model fails on can be left out, as today,
  but the request fails if no chunk produced anything.
- Builds reuse the prebuilt vcpkg tree and run with -j4. GUI test builds run only
  through `scripts/run-dev-isolated.sh`.
- TDD. The pipeline is tested with a fake `Generate`. Controller and UI tests
  use the existing suites (`test/call_notes_pipeline_tests.cpp`,
  `call_notes_controller_tests.cpp`, `call_prompter_pipeline_tests.cpp`,
  `call_prompter_controller_tests.cpp`, `notes_widgets_tests.cpp`,
  `call_notes_page_tests.cpp`, `prompter_panel_tests.cpp`), plus the real-model
  smoke suite for the prompts.

## Decided by the user

- Live: key points and agreements. No running summary.
- After the call: a full summary with the four sections above, after an offer
  the user confirms.
- Next-meeting agreements: an «Add to calendar» button that opens a pre-filled
  event dialog. No automatic creation.
- Summary tasks don't get «Add to calendar» directly. The summary lists the
  accepted agreements first, then the model's extra tasks with «Accept»,
  which moves a task into the agreements ledger. The user said this is fine for
  now and may revisit it after seeing it.
- After the call both live and summary key points are shown.
- Old summaries stay as they are. «Create again» rebuilds them in the new
  format.

## Design

### Live key points

The live notes request (`task: "notes"`, `final: false`) becomes an
incremental key-points request.

- **Input:** only the phrases after the last processed one, plus the texts of
  the most recent live points so the model does not repeat them. The texts are
  for reference only and are never cited.
- **Output:** `{"key_points":[{"text","evidence_ids"}]}`. Each run gives 0–3
  points, each text ≤80 characters, citing that run's new phrases only (the
  schema `enum` of IDs, as now).
- The controller **appends** the validated points to `live.key_points` and
  records how far it has processed. The existing `processed_ms`, or the last
  processed phrase ID, which is more robust to edited timestamps: builder's
  call.
- The live list keeps at most 40 points. When it is full, live runs stop.
- *My call:* a failed run does not move the processed mark, so its phrases are
  retried with the next run (existing backoff). The tail of the call that has
  not been processed when the call ends is not flushed: the worker stops at
  call end, and the summary covers the whole transcript.
- The batching, retry/backoff and failure statuses of
  `CallNotesController` stay as they are.
- A window too large for one call is chunked. Each chunk appends its own
  points. No merge step.
- Live points whose source phrases were later edited or deleted follow the same
  stale and source-warning rules as today's points.

### Agreements: meetings and «Add to calendar»

- The extraction schema gains a meeting marker and structured date/time on each
  event:
  `{"kind","participants","action","evidence_ids","meeting":bool,"date":"YYYY-MM-DD"|"","time":"HH:MM"|""}`
  (key order as listed, because llguidance emits properties in schema order).
- *My call:* a small on-device model resolves relative dates ("в четверг",
  "через неделю") unreliably. The extract payload therefore carries the call
  date and a list of the next ~60 days with their Russian weekday names. The
  schema restricts `date` to an `enum` of those dates or `""`. `time` is
  constrained by a pattern. The C++ side still validates both before use.
- Cards and records carry `meeting/date/time` through accept, edit, reschedule
  merge (`mergeReschedules`) and persistence. When the specialist edits an
  accepted card's text, the stored date and time stay as they were. The dialog
  is where they get corrected.
- **«Add to calendar»** appears only on accepted agreements with
  `meeting: true`: on the prompter cards, and in «For the next meeting» and the
  summary's «Agreements and tasks» in the notes workspace. Summary tasks never
  carry it directly (user's decision), so a re-run of the summary cannot lose an
  «In calendar» state or invite a second event.
  - The new-event dialog (`QEventDetailsWidget` in create mode, as
    `QEventInfoPage::openEventDialog`/`openQuickEventDialog` use it) gets a
    pre-filled template. *My call* on the values:
    - date and time: from the agreement, or the dialog's defaults when empty;
    - client: the client of the call's event;
    - title: the call event's title, or the client's name;
    - duration: the call event's duration, or the dialog default;
    - notes: the agreement text.
  - Only the specialist's save in that dialog creates the event, through the
    normal save path (`onEventSaved`, conflict checker included). Cancelling
    creates nothing.
  - *My call:* after a successful save the agreement stores the new event ID.
    The button becomes «In calendar» and opens that event, so the same
    agreement is not added twice. If the event is later deleted, the button
    returns to «Add to calendar».
  - *My call:* the saved event's ID comes back from the dialog's normal save
    path. The view checks whether the event still exists (`get_event` by ID)
    each time it renders the item. No signal from the calendar is needed.
  - *My call:* when the call has no calendar event or no client, the dialog
    opens with the client empty and the agreement text as the title. The button
    is not hidden.
  - *My call:* "the call date" is the local date of the call: the call event's
    start, or the material's `created_at` when there is no event. It is never
    the date the summary runs, so a summary made days later resolves
    "в четверг" against the call. The summary's leaf calls get the same date
    list and the same `date` enum. Merges keep the validated dates.
  - *My call:* no data migration. Agreements and cards live in the JSON state of
    the prompter and the call material. Old records without the new fields
    count as `meeting: false`, and nothing is re-extracted.

### Full summary after the call

- **Offer.** When the call ends, `finishCall` no longer queues the final run.
  The callSessionEnded wiring in `application.cpp` stops calling
  `finals->enqueue`. If the material has a transcript, `final_status` becomes a
  new `"offered"` state. The page shows «Summarize meeting», whether or not the
  prompter ran during the call. Clicking it calls `requestFinal()`, which goes
  through the existing `CallNotesFinalizer` queue and still waits for the
  transcript to be ready. The offer is also shown when the notes of an
  already-ended meeting that has a transcript but no summary are opened.
- **Output shape** (new `final`, `format: 2`):
  ```json
  {"format":2,
   "overview":{"text":"…","evidence_ids":[…]},
   "key_points":[{"text","evidence_ids"}],
   "tasks":[{"text","evidence_ids","meeting":bool,"date":"","time":""}],
   "open_questions":[{"text","evidence_ids"}]}
  ```
  Limits: overview ≤1000 characters, ≤10 key points of ≤120 characters, ≤8
  tasks, ≤5 open questions of ≤160 characters, 1–8 source IDs per nonempty item.
- **Pipeline** (`processSummary`, next to `processNotes`, which goes away along
  with `notes.txt`/`notes_merge.txt` once nothing uses them). It is a map-reduce
  over chunks like today, but with a fact-oriented leaf and a separate
  overview step, so a long overview never has to pass through every merge.
  *Suggested shape, builder may refine:*
  1. **Leaf per chunk:** a short chunk note (≤300 characters), key points,
     tasks and open questions for that chunk, citing that chunk's IDs.
  2. **Pairwise merge of the lists:** dedupe and cut points, tasks and questions
     to the limits, keeping late facts and corrections. If a merge reply is
     unusable, concatenate the validated items, as `concatenated()` does
     today.
  3. **Overview call:** the chunk notes in order (reduced pairwise first if they
     don't fit) → the overview with evidence.
  The token and byte budgets follow from the 4096 context with a larger output
  reserve for the summary calls. Budgets, call caps and preflight work as in
  `processNotes` today. If the measured budget cannot fit a ~1000-character
  overview, the builder may raise the engine context only after checking memory
  and time on CPU and GPU with the smoke suite. Otherwise shorten the overview
  and note it.
- **Tasks vs. agreements.** The summary request also carries the texts of the
  material's accepted agreements (`loadMaterialAgreements`), as reference only.
  The prompt tells the model not to repeat them as tasks. The C++ side also
  drops a task whose normalized text equals an accepted agreement's. «Accept»
  on a task appends it to the material's agreements
  (`CallNotesController::appendAgreement`, extended with `meeting/date/time`)
  with a fresh ID. The task is then shown as accepted. After a re-run it
  disappears from the task list because it is now an agreement.
- **Display.** The four sections replace today's summary block in
  `NotesWorkspace.qml` and in the widget page (`AiSummaryWidget`,
  `KeyPointsWidget`, `CallNotesPage`). The live points from the call are shown
  in their own block, labelled «From the call» or similar, below the summary's
  key points. Running/queued/error/stale states, Retry, «Create again»,
  «Update», Edit and «Add to my notes» keep their meaning. Edit and «Add to my
  notes» act on the overview text. «Add to my notes» may append all sections:
  builder's call.
- **Old summaries.** A `final` without `format: 2` (only `note` and
  `key_points`) is shown as before: the note as the overview and its points,
  with no tasks or open-questions sections. «Create again» produces format 2.
  Readers of `final`/`live` outside the notes page (`client_notes_journal.cpp`,
  `client_notes_page.cpp`, `meeting_history.cpp`, `application.cpp`
  previews) handle both shapes. Where they show a preview of `note.text`, they
  use `overview.text` for format 2.
- **Live packet.** `live` no longer has a `note`. Readers that fall back from
  `final` to `live.note` show nothing, or the live points, instead.

## Left to the builder

- The exact prompts (Russian, same rules as today) and their real-model
  tuning in `call_prompter_model_smoke_tests.cpp`.
- The exact chunk and output budgets, and whether the summary needs a larger
  context.
- How the notes-page QML reaches the event dialog: a bridge signal wired in
  `application.cpp` to the event page or a standalone dialog.
- How far processing has got (`processed_ms` or a phrase ID).
- Whether the old widget page and the QML workspace share one view-model for
  the new sections.

## Testing

- Pipeline (fake `Generate`): live-points input contains only new phrases.
  Points append and never rewrite earlier ones. The schema `enum` covers only
  that run's IDs. A summary with chunking and a merge fallback keeps late facts.
  The overview step works. Every call passes a non-empty schema, agreement
  calls included. The extract date `enum` comes from the call date.
- Controller: no final run after `finishCall`; `"offered"`; `requestFinal`
  goes through the finalizer; format-2 validation; stale/Update; old-format
  display; the live points cap.
- Prompter: meeting/date/time survive accept/edit/reschedule/persist. The stored
  event ID switches the button.
- UI: «Summarize meeting» appears after the call. The four sections render.
  «Add to calendar» opens a pre-filled dialog, and cancelling it creates no
  event. RU translations exist for every new string.
- Real-model smoke: live points on a synthetic long call, the summary on the
  same call, and a next-meeting date resolved from "в четверг".
