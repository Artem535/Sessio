# Серверное расписание и постоянные приглашения серии

Статус: Draft. Дата: 2026-10-01. Issue: [#98](https://github.com/Artem535/Sessio/issues/98).
Это предлагаемый контракт, а не описание реализованного поведения.

## Назначение

Специалист один раз отправляет клиенту приглашение серии. Сервер хранит копию
расписания, выбирает доступное повторение и выдаёт токены обоим участникам для
одной комнаты этого повторения. Sessio может быть закрыт между встречами.
Постоянное приглашение не означает постоянную комнату или круглосуточный вход.

Sessio остаётся источником расписания. Первая версия поддерживает одного автора
изменений для серии. Редактирование на сервере и полноценная синхронизация всей
базы между устройствами не входят в эту поставку. Внешние ссылки сохраняют
существующее поведение. LLM, промпты и confidence здесь не используются.

Основа: `docs/asciidoc/09-recurring-events.adoc`, ADR приглашений
`docs/asciidoc/12-invitation-security-model-adr.adoc`, локальные
`DuckEventSeries`, `Event`, `EventSeriesException` и `recurrence_utils.cpp`.
Новые методы дополняют API одиночных встреч; его существующие клиенты работают
без изменений. Реализация звонков в активной ветке имеет отдельные встречи с
ограниченным временным окном; свежий main содержит более ранний этап интеграции.

## Модель данных

Сервер хранит семантику локального расписания, но не копию всей DuckDB.
Технический выбор хранилища не требует включать в задачу миграцию из issue #88.

| Объект | Данные и ограничения |
| --- | --- |
| ScheduleSeries | account_id, series_uid (UUID), revision, timezone, dtstart_local, duration_seconds, rrule, until_utc, active |
| OccurrenceOverride | series_uid, original_start_utc, start_utc, end_utc, join_enabled; уникальный ключ (series_uid, original_start_utc) |
| OccurrenceException | series_uid, original_start_utc; подавляет базовое повторение |
| SeriesInvitation | случайный непрогнозируемый код, хеш кода и passcode, generation, failed_attempts, revoked_at; принадлежит серии |
| OccurrenceMeeting | series_uid, original_start_utc, meeting_ref, room_name; уникальный ключ (series_uid, original_start_utc) |

`series_uid` генерируется один раз локально и сохраняется после перезапуска.
Числовой локальный id и отрицательный id виртуального события в API не передаются.
Ключ повторения — его исходное начало до переноса, как у
`original_occurrence_start`. Перенос меняет время доступа, но сохраняет ключ.
Имена клиентов, названия, заметки, цены, платежи и причины отмены не передаются.
Локальные статусы преобразуются в `join_enabled`; canceled/no-show/rescheduled
без действующего перенесённого события не дают вход. Таблицу соответствий
реальных статусов необходимо проверить при реализации, не передавать их db id.

Исключение скрывает базовое повторение. Если на том же ключе есть override,
используется override: это соответствует локальному сценарию переноса.
Дубли ключей внутри массива недопустимы. Список overrides проверяется отдельно
по фактическому времени: перенесённая встреча может попасть далеко от исходной даты.

## Часовой пояс и повторения

Серия закрепляет IANA timezone, например Europe/Moscow, и локальное начало без
UTC offset. Начало отдельного override и ключи исключений передаются в UTC.
Длительность задаётся в секундах реального времени. until_utc включителен для
начала повторения. `active=false` запрещает все новые токены серии.

Клиент и сервер используют один алгоритм RRULE и одинаковые тестовые примеры;
начальный допустимый набор совпадает с daily/weekly/monthly/yearly формой Sessio.
Неизвестные timezone и неподдерживаемые RRULE возвращают 422, без догадок.
Для отсутствующего локального времени при DST повторение пропускается;
для неоднозначного выбирается более ранний UTC instant. Эта политика должна
быть реализована и в клиенте, который сейчас опирается на systemTimeZone.
Смена timezone компьютера не меняет расписание уже привязанной серии.

При миграции timezone старых серий неизвестен. Его следует подтвердить у
специалиста перед первой публикацией серверного расписания, показав ближайшие
даты. Нельзя молча приписывать timezone сервера или предполагать исторический
timezone по текущим настройкам машины. Первое сохранение timezone не должно
самопроизвольно сдвинуть подтверждённые встречи.

## API, версия 1

Все методы специалиста требуют существующую bearer-авторизацию и проверку
account ownership. Ресурсы другого account возвращают 404. UUID не является
средством авторизации. `schema_version=1` обязателен; неизвестные поля отклоняются.

| Метод | Назначение |
| --- | --- |
| PUT /v1/schedule-series/{series_uid} | Атомарно заменить snapshot серии, overrides и exceptions |
| GET /v1/schedule-series/{series_uid} | Получить подтверждённые revision, content_hash и snapshot для восстановления синхронизации |
| POST /v1/schedule-series/{series_uid}/invitation | Создать или явно перевыпустить приглашение серии |
| POST /v1/schedule-series/{series_uid}/revoke | Отозвать текущую generation приглашения |
| POST /v1/schedule-series/{series_uid}/occurrences/{original_start_utc}/specialist-token | Вход специалиста в конкретное повторение |
| POST /v1/invitations/{code}/client-token | Существующий маршрут: дополнительно разрешать приглашение серии |

Пример PUT (все указанные поля обязательны; until_utc допускает null):

```json
{
  "schema_version": 1,
  "revision": 1,
  "base_revision": 0,
  "timezone": "Europe/Moscow",
  "dtstart_local": "2026-10-06T18:00:00",
  "duration_seconds": 3600,
  "rrule": "FREQ=WEEKLY;INTERVAL=1;BYDAY=TU",
  "until_utc": null,
  "active": true,
  "overrides": [],
  "exceptions": []
}
```

Override: `{"original_start_utc":"2026-10-13T15:00:00Z",
"start_utc":"2026-10-14T15:00:00Z","end_utc":"2026-10-14T16:00:00Z",
"join_enabled":true}`. Exception — строка UTC начала базового повторения.
Все UTC значения — RFC3339 с Z и точностью секунд; end > start.
Ограничения v1: snapshot до 1 MiB, до 1000 overrides и 1000 exceptions,
duration до 24 часов, RRULE до 512 байт. Превышение не обрезается: 413/422.

Ответ PUT: `{"series_uid":"UUID","revision":1,"content_hash":"sha256"}`.
Hash считается сервером по нормализованному snapshot без revision/base_revision;
GET возвращает тот же hash. PUT не выдаёт приглашение и не создаёт комнаты.

Первый POST invitation принимает `{"reissue":false}` и Idempotency-Key UUID,
возвращает invitation_url, passcode, generation. Повторная выдача существует
только при явном `reissue=true`: старая generation сразу отзывается.
Если приглашение уже существует, новый запрос с reissue=false возвращает 409
invitation_exists, а повтор с тем же ключом возвращает исходный результат.
Для восстановления после потери ответа сервер сохраняет защищённый replay-ответ
24 часа, клиент сохраняет полученный секрет в защищённом хранилище. После этого
потерянное приглашение можно лишь явно перевыпустить. Код не хранится открытым.

Вход клиента принимает passcode; ответ успешного входа сохраняет существующие
endpointUrl, roomName, token, expiresAt. Персональные данные клиента не нужны.
Ответы с секретами имеют Cache-Control: no-store и не попадают в логи.

## Выбор встречи и создание комнаты

1. Проверить приглашение, его generation, active серии и passcode.
2. Рассчитать базовые повторения в ограниченном окне вокруг server_now,
   применить исключения и overrides, включая переносы извне этого окна.
3. Окно входа: от start минус существующий pre-join buffer до end плюс
   существующий grace period. Используется время сервера, а не клиента.
4. Ноль доступных повторений: 409 occurrence_unavailable. Приглашение
   продолжает действовать для будущих дат. Больше одного: 409
   ambiguous_occurrence; сервер не выбирает встречу произвольно.
5. Для единственного повторения атомарно получить/создать OccurrenceMeeting.
   Уникальный ключ и транзакция гарантируют одну комнату даже при одновременном
   входе клиента и специалиста. Повторный вход использует ту же комнату.
6. Выдать краткоживущий JWT; client identity фиксирован в пределах этой комнаты.

Вход специалиста проходит те же проверки актуального расписания и окна, но
по конкретному ключу повторения, а не по приглашению. Оба пути используют одну
функцию получения комнаты. Существующий endpoint одиночной встречи нельзя
использовать для обхода отмены/переноса: для series-backed meeting он обязательно
проверяет актуальный snapshot серии. Не выдавать JWT по устаревшим stored dates.

Простое изменение календаря закрывает новые входы, но не обрывает текущий звонок.
Уже выданный JWT может действовать до expiry, а участник — оставаться в комнате;
отзыв приглашения не является немедленным отключением участников.
Принудительное завершение через LiveKit — отдельная будущая команда.

В этой поставке нет новой публичной страницы с расписанием. Вне окна клиент
видит «Сейчас нет доступной встречи», без раскрытия ближайших дат до проверки
секретов. Если потребуется показывать ближайшую встречу, нужен отдельный контракт.

## Синхронизация и работа без сети

Локальное сохранение и durable outbox выполняются в одной транзакции.
Изменение всей серии, перенос, отмена и прекращение повторений ставят новый
полный snapshot в очередь. Отсутствие override/exception в новом snapshot
означает удаление ранее переданной записи. Это не частичный PATCH.

Первое создание использует base_revision=0. Новое обновление проходит только
если base_revision совпадает с сервером и revision=base_revision+1. При потере
ответа клиент повторяет тот же snapshot с теми же revision: совпадающее содержимое
возвращает прежний успех; отличающееся — 409 revision_conflict. Старый snapshot
не может восстановить отменённую встречу. PUT коммитится одной транзакцией;
невалидный запрос не меняет ни одну из трёх коллекций.

Пока один snapshot в полёте, последующие локальные изменения ждут. После ACK
формируется следующий snapshot с актуальным локальным состоянием. ACK старой
версии не помечает более новые изменения синхронизированными. Перезапуск
восстанавливает очередь. Сохраняются last_ack_revision и desired_local_revision.

UI показывает: «Отправляется», «Синхронизировано», «Ожидает сети», «Конфликт».
После локальной отмены без ACK явно сообщает: «Сервер ещё может разрешать вход
по прежнему расписанию». Новое приглашение можно копировать после публикации
расписания и получения ответа invitation. Существующая ссылка продолжает
использовать последнюю подтверждённую серверную версию во время offline.

Восстановление старого backup не сбрасывает revision автоматически. При конфликте
GET позволяет сравнить состояния; автоматическая перезапись сервера запрещена.
Явное действие «Опубликовать восстановленное расписание» отправляет новую версию
поверх подтверждённой серверной, после просмотра различий. Это также граница
первой версии для второго устройства; полноценный multi-writer merge отложен.

## Ошибки, повторы и ограничения

| HTTP / error | Действие клиента |
| --- | --- |
| 401 unauthorized | Получить/исправить credential; не повторять бесконечно |
| 404 not_found | Проверить account/resource; неизвестный код не раскрывает расписание |
| 409 revision_conflict | Остановить очередь серии, получить server snapshot, показать конфликт |
| 409 occurrence_unavailable / ambiguous_occurrence | Не выдавать токен; показать недоступность или конфликт расписания |
| 410 invitation_revoked | Попросить новое приглашение |
| 413 / 422 invalid_schedule | Сохранить локальные изменения; показать причину и остановить автоматические повторы |
| 429 too_many_attempts | Соблюдать Retry-After; заблокированное приглашение требует перевыпуска |
| 5xx / timeout | Повторить безопасную операцию с тем же содержимым/ключом |

Клиентский timeout — 15 секунд. Outbox retry с jitter: 2, 5, 15, 60 секунд,
затем до 5 минут; сеть/ручной retry будят очередь. Token retry не создаёт новую
комнату. Сервер ограничивает sync 60/min/account, invitation mutation
10/min/account, token exchange 30/min/account или invitation. Для новой series
invitation сохраняется отдельный строгий лимит пяти неверных passcode и отзыв
при шестой ошибке; лимит не сбрасывается еженедельно. Счётчик изменяется атомарно.
Действующая политика одиночных приглашений сохраняется; изменения способа
доставки passcode не входят в эту задачу.

Вычисление RRULE ограничено по времени/числу итераций. При исчерпании бюджета
вычисления (100 ms / 10000 итераций) — 503 schedule_resolution_unavailable,
без токена и без fallback в другую комнату. Перед реализацией подтвердить
бюджет на длинных сериях и одинаковую стратегию быстрого поиска у клиента/сервера.
Точность совпадения расписания проверяется тестами, не оценкой confidence.

## Миграция и поставка

1. Реализовать общий проверяемый расчёт повторений с явной timezone.
2. Добавить серверные таблицы, атомарный snapshot API и resolver комнаты.
3. Добавить локальные UUID/timezone/outbox, состояния отправки и операции
   приглашения серии; разделить series invitation и occurrence meeting_ref.
4. Старые одиночные встречи продолжают работать. Старую серию с одним
   meeting_ref подключать к новому механизму только явной миграцией: сначала
   синхронизировать расписание, затем создать постоянное приглашение, после
   подтверждения отключить старое и попросить отправить новую ссылку один раз.
   При сбое оставить старую связь; не обещать сохранить старую ссылку.
5. Выполнить миграционные round-trip/restore тесты и реальный smoke на staging.
   Включать поддержку после обновления обеих сторон. Серверные записи сохранять
   при rollback клиента; downgrade не должен превращать повторения в одиночную
   комнату. Lifecycle/очистку истории и лимит хранения определить до production.

Для «это и последующие» при создании новой локальной серии постоянное
приглашение должно сохранять маршрутизацию на её преемника: сервер хранит цепочку
сегментов под одним приглашением, с непересекающимися границами действия.
Контракт атомарной замены сегментов требует отдельного дополнения. До его
реализации UI должен блокировать такую операцию для синхронизированной LiveKit
серии с объяснением; не создавать молча новую ссылку. Первая поставка покрывает
изменение одного повторения и всей серии, не скрывая это ограничение.

## Приёмка

- Две еженедельные встречи: одна ссылка, разные комнаты; специалист и клиент
  попадают в одну комнату нужной даты. Повторный вход не создаёт новую комнату.
- Три параллельных запроса (клиент, специалист, повтор клиента) создают одну
  запись meeting. Календарное окно закрывается и открывается корректно.
- Перенос одного повторения сохраняет ключ и приглашение, закрывает старое
  время и разрешает новое; дальний перенос тоже находится resolver.
- Отмена одного повторения не мешает следующему; прекращение серии запрещает
  новые токены. Старая generation после перевыпуска не работает.
- Offline отмена, потеря ACK, перезапуск, повтор snapshot и старый backup не
  восстанавливают отмену на сервере без явной публикации новой версии.
- DST, разные timezone хостов, месяцы без нужного дня, until, исключения и
  overrides дают одинаковые UTC начала на клиенте и сервере.
- Пересечение окон двух повторений отвечает ambiguous_occurrence без токена;
  UI предупреждает о таком пересечении, в том числе после переносов.
- Чужой account не читает и не меняет серию. Секреты и клиентские поля
  отсутствуют в логах. Новая схема БД проходит restore/round-trip.
- Реальный staging smoke: клиент входит по одной ссылке в два повторения,
  второе при закрытом Sessio до старта; после входа специалиста есть двусторонние
  аудио/видео. HTTP 200 и unit tests сами по себе не являются этим smoke.

До реализации дополнить: точное соответствие статусов, общий recurrence module,
политика хранения серверной истории и контракт будущего split серии. Эти пункты
не означают, что описанные API или синхронизация уже существуют.
